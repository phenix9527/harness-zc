### ★ Windows PowerShell 用户先看这一段

本文档里的示例命令是 **Bash / Git Bash** 风格（`curl -H ... -d ...`）。在 Windows PowerShell 里，
`curl` 是 `Invoke-WebRequest` 的**别名**，参数体系完全不同，直接粘贴会报：

```
无法绑定参数"Headers"。无法将"System.String"类型的"Content-Type: application/json"值
转换为"System.Collections.IDictionary"类型。
```

三个选择：

1. **用现成的脚本**（推荐）：`doc/demo-requests.ps1` 把五个场景的调用和预期结果全写好了。

   ```powershell
   # 直接双击运行会被执行策略拦下，用这个方式跑：
   powershell -ExecutionPolicy Bypass -File .\doc\demo-requests.ps1
   # 换端口 / 换测试数据
   powershell -ExecutionPolicy Bypass -File .\doc\demo-requests.ps1 -BaseUrl http://127.0.0.1:18080 -UserId 8801
   ```

2. **手写等价命令**：

   ```powershell
   $BASE = "http://127.0.0.1:8080"
   Invoke-RestMethod -Method Post -Uri "$BASE/inner/coupon/SPRING_2026/claim" `
       -ContentType "application/json" -Body '{"userId":8801}'
   # 需要自定义头时（注意 Headers 是哈希表，不是字符串）
   Invoke-RestMethod -Method Post -Uri "$BASE/inner/export/tasks" -ContentType "application/json" `
       -Headers @{ "X-User-Id" = "8801" } -Body '{"requestId":"r1","bizType":"ORDER","queryJson":"{\"rows\":100}"}'
   ```

3. **坚持用 curl**：必须显式写 `curl.exe`（否则走的还是别名），且 JSON 要转义引号：
   `curl.exe -s -X POST $BASE/... -H "Content-Type: application/json" -d '{\"userId\":8801}'`。
   不转义的话 PowerShell 5.1 会把双引号吃掉，服务端收到非法 JSON。

> 另外两条 5.1 的坑，写脚本时必踩（`demo-requests.ps1` 里都绕过了）：
> ① `.ps1` 文件含中文时**必须存成 UTF-8 with BOM**，否则按 GBK 解码直接解析失败；
> ② 接口返回 `application/json` 不带 charset，`Invoke-RestMethod` 会按 ISO-8859-1 解码 → 中文乱码，
> 要取原始字节自己按 UTF-8 解。

### 标准答案：你该看到的命令序列

（实测抓取，用户 `8802`；顺序可能微调，结构一定长这样）

```text
① EVALSHA <limitSha> 1 rate:coupon:user:8802     1  1        -> [lua] INCR + EXPIRE 1
② EVALSHA <limitSha> 1 rate:coupon:ip:127.0.0.1 10 60        -> [lua] INCR + EXPIRE 60
③ GET   activity:info:SPRING_2026        （未命中，回源 DB）
   SETEX activity:info:SPRING_2026 60 {...}                  -> 活动缓存，60 秒
④ EVALSHA <claimSha> 2 coupon:stock:1 coupon:user:1:8802 604800
      |- [lua] SETNX  coupon:user:1:8802        幂等标记，返回 1 = 首次
      |- [lua] GET    coupon:stock:1            87
      |- [lua] DECR   coupon:stock:1            86
      |- [lua] EXPIRE coupon:user:1:8802 604800 7 天
⑤ [Java 侧] INSERT INTO t_coupon -> id=14, status=0
```

每一步在说什么：

| 你看到的 | 说明了什么 |
| --- | --- |
| ①② 排在最前面 | **限流先于幂等**。同一 userId 连打时，第二次可能先被限流拦成 `20010`，根本走不到幂等判断 —— 想观察 `newlyClaimed=false` 必须等过窗口（用户维度 1 秒） |
| ① 过期 1 秒 / ② 过期 60 秒 | 用户维度 1 次/秒、IP 维度 10 次/分钟。看到 `retryAfter` 时用它反推撞的是哪一档：约 1 是用户维度，约 60 是 IP 维度 |
| ③ 缓存 60 秒 vs ④ 标记 7 天 | 活动配置缓存和用户幂等标记是**两个互不相干的生命周期**，别混为一谈 |
| ④ 里四条命令嵌在一组 | `SETNX` 判断与 `DECR` 扣减之间**没有任何空隙**，这正是 Lua 原子的意义。拆成两段 Java 代码（先 `setIfAbsent` 再 `decrement`），中间进程挂掉就会出现「扣了库存但标记没打上」—— 这就是超发的来源 |
| ⑤ 库存 87 → 86，DB 多一行 | Redis 扣减与 DB 落库各自留痕，两边必须对得上 |

> ⚠️ ④ 里 `EVALSHA` 与完整 `EVAL` **同时出现是正常的**：脚本缓存未命中时客户端会降级重发脚本体（Spring Data Redis 行为）。
> 判断有没有执行两次，**只看带 `[lua]` 的那几行内部命令** —— 只有一组，就说明只执行了一次。

### 一次请求的全链路（先看这张图）

上面那份文件清单，其实就是这张图的零件。读代码时对照着走：

```text
POST /inner/coupon/{activityCode}/claim
│
├─ ① 限流            CouponClaimService:108 → RedisRateLimiter
│     rate:coupon:user:{userId}    1 次 / 秒
│     rate:coupon:ip:{ip}         10 次 / 分钟
│     ★ 省资源手段，不是正确性手段：挡的是「同一人/同一 IP 刷接口」，
│       挡不住「不同用户同时涌入」——那种要靠全局维度限流，本项目没有
│
├─ ② 活动校验        :113 → ActivityCache（Caffeine + Redis 二级）
│     不存在 → 20000 ；不在时间窗 → 20003
│     ★ 用服务端时间判断，绝不用客户端传的时间
│
├─ ③ 幂等第 1 层     :128  DB 快查 selectByUserAndActivity
│     命中 → 返回上次那张券（newlyClaimed=false），不进 Lua
│     成本最低所以放最前；只挡串行重复（用户点两次），挡不住并发
│
├─ ④ 幂等第 2 层     :142  Redis Lua 原子预扣（coupon_claim.lua）
│     SETNX coupon:user:{activityId}:{userId}   ★ 必须带 userId，才是「一人一单」
│          ├─ 0 ──→ return -1（已领）→ 回查 DB（重试 3 次，:236）
│          └─ 1
│     GET coupon:stock:{activityId}（key 不存在时按 0 处理）
│          ├─ <= 0 ──→ DEL 用户标记 + return -2（抢光）  ★ 不 DEL 会误伤用户
│          └─ > 0
│     DECR 库存 → EXPIRE 标记 604800s（7 天）→ return 剩余库存
│
└─ ⑤ 幂等第 3 层     :176  INSERT t_coupon（status=0 未使用）
      └─ DuplicateKeyException → INCR 回补库存 → 返回上次那张券
         ★ 不回补 = 每次并发穿透白扣一份库存 = 库存泄漏、少发券
         ★ 谁能撞上它：撞 uk_user_activity(user_id, activity_id) 的
           只可能是「同一用户 + 同一活动」——其他用户根本撞不上这个索引。
           而且正常双击走不到这（SETNX 已把第二个请求挡成 -1 分支），
           真落到这 = Redis 标记防线失效（主从切换丢标记 / 被误删，见阶段4实验1）
```

**这张图的读法**：`④` 里有三种出口（剩余库存 / `-1` / `-2`），正好对应 `coupon_claim.lua` 的三种返回值；
而 `③④⑤` 合起来才是完整幂等 —— 快查挡串行、Lua 标记挡并发、唯一索引兜底。

### 领券链路上的 5 个 key（别记混）

同一份代码里 5 个 key，形态和寿命都不一样，这是最容易记串的地方：

| key | 形态 | 谁写的 | 寿命 |
| --- | --- | --- | --- |
| 库存 | `coupon:stock:{activityId}` | 预热任务 `warmUpStock`（`:210`） | 配置的 TTL，须覆盖活动期 + 余量 |
| 用户标记 | `coupon:user:{activityId}:{userId}` | Lua `SETNX` | `ARGV[1]`，默认 **604800s / 7 天** |
| 用户限流 | `rate:coupon:user:{userId}` | `RedisRateLimiter` | **1 秒** |
| IP 限流 | `rate:coupon:ip:{ip}` | `RedisRateLimiter` | **60 秒** |
| 活动缓存 | `activity:info:{activityCode}` | `ActivityCache` 回源后写 | **60 秒** |

两个容易踩的坑：

1. **用户标记必须带 `userId`** —— 形态是 `coupon:user:{activityId}:{userId}`，不是 `coupon:user:{activityId}`。只到活动维度的标记毫无意义：「一人一单」的判据就是「这个人 × 这个活动」的组合。拼装在 `CouponClaimService:141`（`USER_MARK_KEY_PREFIX + act.getId() + ":" + userId`）。
2. **同一个活动有两种标识**：库存和用户标记用**自增 id**（`1`），活动缓存用 **activityCode**（`SPRING_2026`）。前者是内部主键，后者是对外防遍历的标识 —— 两套 ID 混用是这类缓存的经典事故来源。

### ★ 三个最容易记错的点

这三个坑在读代码时很容易滑过去，但每一个对应一次线上事故：

| 容易记成 | 实际是 |
| --- | --- |
| 限流是为了「防止服务被瞬时流量打垮」 | 用户 1 次/秒 + IP 10 次/分钟**挡不住瞬时流量**（不同用户 IP 各异）。它防的是刷接口，别拿它当秒杀保护 |
| 「`SETNX` 返回 1 就继续走流程」 | `SETNX` 的 1 是 **Redis 命令内部**的返回值。Lua **对外**只返回 `剩余库存` / `-1` / `-2`，Java 判断的是 `left == -1L`、`left == -2L` |
| Redis 扣完就万事大吉 | 有两个**反向补偿**动作漏一个就出事：库存不足要 `DEL` 标记（否则用户没领到却被挡 7 天）；撞唯一索引要 `INCR` 回补（否则库存泄漏、少发） |

> 检验方法：如果你能把「限流为什么不是正确性手段」和「哪两处需要反向补偿」讲给别人听，这一阶段的核心就抓住了。

### 动手：手动把 Lua 的三种返回值都跑一遍

这一步能让你彻底理解「原子性」的价值。别只看代码，**跑**：

```bash
BASE=http://127.0.0.1:8080
cd /d/idea/api-demo
LUA=$(cat src/main/resources/lua/coupon_claim.lua)

# 造一个独立的测试活动库存：5 个
docker exec apidemo-redis redis-cli SET "coupon:stock:999" 5
docker exec apidemo-redis redis-cli DEL "coupon:user:999:1"

# 第一次：返回 4（扣减后的剩余库存）
docker exec apidemo-redis redis-cli EVAL "$LUA" 2 "coupon:stock:999" "coupon:user:999:1" 604800

# 第二次：返回 -1（同一用户，幂等命中）
docker exec apidemo-redis redis-cli EVAL "$LUA" 2 "coupon:stock:999" "coupon:user:999:1" 604800

# 换个用户，连跑到库存耗尽：最后一个返回 -2
for u in 2 3 4 5 6; do
  docker exec apidemo-redis redis-cli EVAL "$LUA" 2 "coupon:stock:999" "coupon:user:999:$u" 604800
done
```

**要体会的点**：`SETNX` 判断和 `DECR` 扣减之间**没有任何空隙**。  
如果拆成两段 Java 代码（先 `setIfAbsent` 再 `decrement`），中间进程挂掉就会出现  
「扣了库存但标记没打上」——这就是超发的来源。

### 动手：亲手撞一次唯一索引

```bash
docker exec apidemo-mysql mysql -uroot -p123456 -D api_demo -e "
  INSERT INTO t_coupon (user_id, activity_id, coupon_no, status, expire_time)
  VALUES (8888, 1, 'C-DUP-1', 0, DATE_ADD(NOW(), INTERVAL 30 DAY));
  INSERT INTO t_coupon (user_id, activity_id, coupon_no, status, expire_time)
```

第二条会报 `Duplicate entry '8888-1' for key 'uk_user_activity'`。  
**这个异常不是错误，是设计**——它是并发穿透时的最后一道闸门。

## 实验 4　停掉 Redis：看降级行为

**目的**：搞清楚每个组件挂掉之后，系统到底是 fail-open 还是 fail-close。

```bash

docker stop apidemo-redis
```

**预期与结论**：

| 组件 | 行为 | 为什么 |
|---|---|---|
| 限流器 | **fail-open**（放行），只打 error 日志 | 限流挂了不该把业务拖垮（见 `RedisRateLimiter` 注释第 3 条） |

| health | `DOWN` | Actuator 的 Redis 健康指示器 |

注释里给了答案（建议 fail-close），但你要能自己论证。

## 实验 5　看门狗与锁 TTL

**目的**：理解 Redisson 看门狗到底解决了什么，以及为什么不能用固定租期。

```bash
# 1) 把看门狗超时改小，让定时任务耗时超过它
#    application.yml: demo.lock.watchdog-timeout-millis: 2000
# 2) 重启应用，然后挂上 monitor 等定时任务（每 2 分钟一次）
docker exec apidemo-redis redis-cli monitor | grep -i "lock:job"
```

**预期**：你会看到 `pexpire` **反复出现**（每约 1/3 超时时间一次）——
这就是看门狗在续期。默认 30000ms 时，续期间隔 10s。

```bash
# 对照组：把 RedissonLock 换成三参数 tryLock(key, wait, leaseTime, unit)
mvn -Dtest=RedissonLockTest test
```

**预期**：单测**变红**。那条 `verify(lock, never()).tryLock(anyLong(), anyLong(), any(TimeUnit.class))`
就是为此写的 —— 它是一道防止有人「顺手改成固定租期」的护栏。
**结论**：固定租期的锁，任务跑超时就会被第二个副本抢到 → 重复执行。
而 CAS 只能保证不出错，**保证不了不重复做无用功**。

## 实验 6（进阶）　把 MQ 发送放进事务里

**目的**：理解 `afterCommit` 的必要性。

1. 把 `ExportTaskService` 里的 `afterCommitExecutor.execute(...)` 换成直接
   `rabbitTemplate.convertAndSend(...)`。
2. 在其后人为抛一个异常，触发事务回滚。
3. 观察：消费者收到消息 → 按 taskId 查任务 → **查不到**（因为事务回滚了）。

**结论**：消息已经发出去了，但业务数据不存在。消费者只能空转或报错。
`afterCommit` 解决的是这个；而它**没解决**的是「提交成功但消息没发出去」——
那需要本地消息表或事务消息（业务数据与待发消息同库同事务落盘，再由投递线程发送）。
