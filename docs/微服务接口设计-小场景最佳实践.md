# 微服务接口设计：小场景最佳实践

> 5 个日常场景，每个都能独立跑通、代码量不大，但把接口设计的核心「五脏」都覆盖到了。
> 技术栈按 Spring Boot 2.x + MyBatis + Redis + MQ 写。

---

## 0. 先定义什么叫「五脏俱全」

任何一个**写接口**上线前，必须能回答这 7 个问题（前 5 个是硬性的）：

| 器官 | 要回答的问题 |
|---|---|
| 契约 | Req/Resp DTO 是什么？字段语义清晰吗？ |
| 校验 | 参数合法性 + 业务前置条件都查了吗？ |
| 幂等 | 重复调用会怎样？靠什么兜底？ |
| 并发 | 同时来两个相同请求会怎样？ |
| 错误语义 | 这是业务失败还是系统异常？调用方该不该重试？ |
| 状态机 | 当前状态允许执行这个操作吗？ |
| 可观测 | traceId 传了吗？关键路径有日志/指标吗？ |

### 统一骨架（后面 5 个场景都基于它）

```java
public class Result<T> {
    private int code;        // 0=成功；非 0=业务失败
    private String message;
    private T data;
    public static <T> Result<T> ok(T data) { ... }
    public static <T> Result<T> fail(ErrorCode ec) { ... }
}

// 错误码分段：1xxxx 参数类 / 2xxxx 业务类 / 3xxxx 系统类
public enum ErrorCode {
    PARAM_INVALID(10001, "参数不合法"),
    COUPON_ALREADY_CLAIMED(20001, "已领取过"),
    COUPON_SOLD_OUT(20002, "已抢光"),
    COUPON_NOT_RUNNING(20003, "活动未开始或已结束"),
    SEND_TOO_FREQUENT(20004, "发送过于频繁"),
    SYSTEM_ERROR(30001, "系统繁忙，请稍后重试");
}
```

**核心约定：业务失败返回 HTTP 200 + `code != 0`，只有系统异常才返回 HTTP 5xx。**

这一条是给调用方的唯一判断依据——看到 200 + code≠0 说明「这事办不成，别重试了」；看到 5xx 说明「我这出问题了，你可以重试」。混在一起，调用方就只能瞎猜。

## 场景 1：优惠券领取（高并发写入样板）

**为什么选它**：一个接口里同时出现幂等、超卖、状态机、限流、异步，是最典型的「五脏俱全」。

### 接口

```
POST /inner/coupon/{activityCode}/claim
ClaimCouponReq  { Long userId; }
ClaimCouponResp { String couponNo; Integer status; }
```

### 关键实现

```java
public ClaimCouponResp claim(String activityCode, ClaimCouponReq req) {
    Activity act = activityCache.get(activityCode);

    // 1. 状态机守卫：活动必须在进行中
    if (!act.isRunning()) throw new BizException(COUPON_NOT_RUNNING);

    // 2. 幂等语义：已领过 ===> 直接返回上次结果，而不是报错
    Coupon existing = couponMapper.selectByUserAndActivity(req.getUserId(), act.getId());
    if (existing != null) return ClaimCouponResp.of(existing);

    // 3. 并发防护：Redis 原子预扣（库存 DECR + 用户标记 SETNX 用 Lua 保证原子）
    Long left = redis.execute(CLAIM_LUA, stockKey, userKey);
    if (left == null) throw new BizException(COUPON_SOLD_OUT);      // 库存不足
    if (left == -1L) {                                              // SETNX 失败 = 已领过
        redis.incr(stockKey);                                       // ★ 回补，否则库存泄漏
        return ClaimCouponResp.of(couponMapper.selectByUserAndActivity(...));
    }

    // 4. 最终防线：唯一索引 uk_user_activity(user_id, activity_id)
    try {
        Coupon c = buildCoupon(req.getUserId(), act);
        couponMapper.insert(c);
        return ClaimCouponResp.of(c);
    } catch (DuplicateKeyException e) {                             // 并发穿透到这里
        redis.incr(stockKey);
        return ClaimCouponResp.of(couponMapper.selectByUserAndActivity(...));
    }
}
```

### 要点

- **Redis 只负责「挡在前面减少无效请求」，正确性靠 DB 唯一索引兜底。** 唯一索引不是可选项，没有它，Redis 挂了或 Lua 写错就是超发。
- **幂等要返回「已领取的结果」，不是返回错误。** 用户点两次，第二次看到「已领取」是正常体验；返回 500 会让前端以为失败去重试。
- **预扣失败必须回补**，否则并发穿越时会漏掉库存。
- 更进一步的削峰版本：Redis 扣减成功就返回成功，发 MQ 异步落库，DB 只做最终一致。代价是用户可能拿到一个「还在生成中」的券。
- 限流放在最前面（用户维度 1 次/秒、IP 维度 10 次/分钟），别让请求打到 Redis。

## 场景 2：支付回调通知（幂等 + 状态机守卫的教科书）

**为什么选它**：外部依赖主动推给你，你无法控制它推几次、什么时候推。这是最容易出事故的一类接口。

### 接口

```
POST /notify/wechat/pay     ← 支付网关调用，不是前端调用
```

### 关键实现

```java
@PostMapping("/notify/wechat/pay")
public String wxPayNotify(HttpServletRequest request) {
    String body = readBody(request);

    // 1. 验签，不通过直接拒（防止伪造回调）
    if (!wxPayVerifier.verify(request.getHeader("Wechatpay-Signature"), body)) {
        return "{\"code\":\"FAIL\",\"message\":\"sign error\"}";
    }
    PayNotify notify = JSON.parseObject(body, PayNotify.class);

    try {
        orderService.handlePaid(notify);
    } catch (BizException e) {
        // 业务上已经处理过 → 返回成功，别让微信一直重试
        log.warn("notify ignored, outTradeNo={}", notify.getOutTradeNo(), e);
    } catch (Exception e) {
        // 系统异常 → 返回失败，让微信重试（默认会重试 8 次）
        log.error("notify handle error, outTradeNo={}", notify.getOutTradeNo(), e);
        return "{\"code\":\"FAIL\",\"message\":\"system error\"}";
    }
    return "{\"code\":\"SUCCESS\",\"message\":\"ok\"}";
}
```

```java
// ★ 一行 CAS 同时解决「幂等」和「状态机守卫」
int rows = orderMapper.updateStatusToPaid(orderId, WAIT_PAY, PAID);
if (rows == 0) {
    log.info("duplicate or illegal state, orderId={}", orderId);
    return;   // 已处理过 / 状态不对，静默返回，不再往下走
}
// 只有真正完成状态流转的那一次，才会执行后续业务
couponService.issue(orderId);
mqTemplate.send(ORDER_PAID_TOPIC, orderId);
```

对应的 SQL：

```sql
UPDATE txm_order SET status = #{to}, pay_time = NOW()
WHERE id = #{id} AND status = #{from}   -- ← 精髓在这一行
```

### 要点

- **`UPDATE ... WHERE status = 期望值` 的一行 CAS，是性价比最高的写法**：一条 SQL 同时保证「重复通知不会重复处理」和「非法状态不会流转」。不需要分布式锁，不需要额外幂等表。
- **回调必须按网关规定的格式返回**（微信要 `{"code":"SUCCESS"}` 这种特定体）。返回错格式 = 网关认为失败 = 无限重试，能把你的服务打挂。
- **回调里只做落库 + 发 MQ，不要做重业务**。网关有 5s 超时，超时就重试，越重的逻辑越容易雪崩。
- **业务失败返回成功、系统失败返回失败**——这个区分在回调场景里是必须的，否则你一个数据库抖动就会被网关判成永久失败。
- 回调天然会乱序/重复，**不要依赖回调返回的金额**，以自己订单表的金额为准。

## 场景 3：短信验证码发送（限流 + 频控样板）

**为什么选它**：写接口里最少代码，但限流维度最全，而且错误语义（带 retryAfter）直接影响前端体验。

### 接口

```
POST /inner/sms/code
SendSmsReq { String mobile; SmsScene scene; }
```

### 关键实现

```java
public void sendSmsCode(String mobile, SmsScene scene) {
    // 多维度频控：任一命中即拒绝，返回剩余秒数（而不是抛 500）
    long ttl = rateLimiter.tryAcquire(mobile, scene);
    // 内部三段：同一手机号 60s 内 1 次 / 1h 内 5 次 / 24h 内 20 次
    if (ttl > 0) {
        throw new BizException(SEND_TOO_FREQUENT, "请 " + ttl + " 秒后重试");
    }

    String code = RandomStringUtils.randomNumeric(6);
    redis.setex("sms:code:" + scene + ":" + mobile, 300, code);   // 5 分钟有效
    smsClient.send(mobile, scene.getTemplate(), code);            // 发送失败要记日志/回滚计数
}
```

校验侧：

```java
public void verify(String mobile, SmsScene scene, String input) {
    String key = "sms:code:" + scene + ":" + mobile;
    String code = redis.get(key);
    if (code == null || !code.equals(input)) throw new BizException(CODE_INVALID);
    redis.del(key);   // ★ 校验成功立即失效，防重放
}
```

### 要点

- **频控用 Redis `INCR + EXPIRE` 固定窗口就够**，不用上 Sentinel。三个维度（60s / 1h / 24h）各一个 key。
- **错误信息要带 retryAfter**，前端才能做倒计时。只返回「操作过于频繁」，用户会一直点。
- **验证码校验成功后立刻 delete**，否则同一个码可以被重放多次。
- **不要暴露手机号是否存在**（登录场景），返回文案统一成「验证码已发送」。
- 防刷兜底：同 IP 限流 + 图形验证码门槛 + 黑名单。短信是按条计费的，被刷是真花钱。

## 场景 4：订单超时自动关闭（延迟消息 + 幂等）

**为什么选它**：延迟消息 + CAS 的组合，是「异步任务如何安全写数据」的标准答案。

### 关键实现

下单成功后发延迟消息：

```java
// RocketMQ 延迟等级 / RabbitMQ 死信队列 + TTL / Redis ZSet + 定时扫描
mqTemplate.sendDelay(ORDER_TIMEOUT_TOPIC, orderId, 30, TimeUnit.MINUTES);
```

消费侧：

```java
@RabbitListener(queues = ORDER_TIMEOUT_QUEUE)
public void onTimeout(Long orderId) {
    // ★ 又是 CAS：只有还是「待支付」才允许关单
    int rows = orderMapper.closeIfWaitPay(orderId);
    if (rows == 0) {
        log.info("order already paid or closed, skip. orderId={}", orderId);
        return;
    }
    stockService.release(orderId);       // 释放预占库存
    couponService.revoke(orderId);       // 退还优惠券
}
```

```sql
UPDATE txm_order SET status = 4 /* 已关闭 */, close_time = NOW()
WHERE id = #{orderId} AND status = 1 /* 待支付 */
```

### 要点

- **`WHERE status = 待支付` 一次解决两个问题**：用户 29:59 支付、30:00 消息到达时不会误关已支付订单；消息重复投递也不会关两次。
- **延迟消息必须有兜底定时任务扫表**。消息丢了（MQ 重启、topic 被误删）就意味着订单永远挂着占库存。定时任务扫 `status=待支付 AND create_time < NOW() - 30min` 是必需的第二道防线，不是可选优化。
- **不要用分布式锁**。CAS 足够了，而且天然幂等。
- 关单后要释放的关联资源（库存、优惠券）也要各自幂等，不能因为订单已关就假设资源没释放过。

## 场景 5：异步导出报表（长任务样板）

**为什么选它**：任何耗时超过 3 秒的操作，都不该用同步接口扛。这是最容易一开始就设计错的场景。

### 接口

```
POST /inner/export/tasks
ExportTaskReq { String requestId; String bizType; String queryJson; }
→ { taskId: "E20260929001", status: "PENDING" }

GET /inner/export/tasks/{taskId}
→ { status: "RUNNING", progress: 65, resultUrl: null, expireAt: null }
→ { status: "SUCCESS", progress: 100, resultUrl: "https://...", expireAt: "2026-10-06 10:00" }
```

### 关键实现

```java
@PostMapping("/inner/export/tasks")
public Result<ExportTaskResp> submit(@Valid @RequestBody ExportTaskReq req) {
    // 幂等：requestId + userId 唯一索引，重复提交返回同一个 taskId
    ExportTask task = exportService.createOrGet(req);
    return Result.ok(ExportTaskResp.of(task));
}
```

状态机只允许单向流转，且用 CAS 更新：

```java
// 执行器侧
int rows = taskMapper.markRunning(taskId);        // WHERE status = 'PENDING'
if (rows == 0) return;                            // 已被别的 worker 抢走，直接退出
doExport(taskId);
taskMapper.markSuccess(taskId, fileUrl, expireAt);
```

### 要点

- **长任务永远不要用同步接口扛**。Feign 默认超时、网关超时、Nginx 超时，任何一层都会把你坑死，而且客户端断开后你的线程还在跑。
- **接口语义要三个明确**：提交返回 taskId、查询返回状态与进度、结果带 `expireAt`。
- **结果文件必须有有效期 + 定时清理**，否则半年后磁盘爆掉，而且没人承认是自己写的功能。
- **状态机单向流转**：`PENDING → RUNNING → SUCCESS / FAILED`，用 CAS 更新，避免多 worker 重复消费。
- 客户端轮询要退避（1s → 2s → 5s → 10s），或者干脆提供回调通知，别让人家 200ms 轮一次。

## 三条贯穿所有场景的结论

1. **幂等的正确性永远靠 DB 唯一约束 / 条件更新兜底。** Redis、分布式锁、本地缓存都只是「挡流量」的手段，不能作为正确性依据——它们会挂、会过期、会写错。

2. **`UPDATE ... WHERE status = 期望值` 这一行 CAS，同时解决「幂等」和「状态机守卫」。** 靠 `affected rows == 0` 判断「这次操作是不是有效的那一次」，是投入产出比最高的写法。写接口时先想这一行 SQL 该怎么写，剩下的逻辑自然就清晰了。

3. **业务失败返回 HTTP 200 + `code != 0`，系统异常返回 5xx。** 这是调用方判断「能不能重试」的唯一依据。区分不清，重试就会变成重放，或者该重试的不重试。

- **Google AIP（google.aip.dev）** — 精读 AIP-132/158（分页）、AIP-193（错误模型）、AIP-180（向后兼容）、AIP-151（长任务）

- **Seata TCC 文档** — 分布式事务接口必须满足的三条约束：幂等、允许空回滚、防悬挂
